### 关于 `STALE` 的口径：不许拿它洗掉已发生的失败

新增图绑定检查后（TD-UAPP-09），`UAPP-GAP-01` 与 `UAPP-WITHDRAW-01` 的归档证据
被机器判成 `NOT_VERIFIED / STALE`——因为它们绑在旧图上。

**这两条不得因此被读成「不再是失败」。** `STALE` 说的是「这份证据只证明旧图」，
不是「那次失败没发生过」。已发生的事实不会因为图改了就消失：

- **AC-06**：根因是逐字复用的 M1 对话节点，本任务**从未改动过它**，缺陷原封不动仍在。
  这里连「修好了但没复验」都谈不上，就是没修。**照记 `FAIL`。**
- **AC-07**：修复已部署（撤回轮不再进 M3），但**没有做过一次端到端复验**。
  「部署了修复」不是「验证了修复」。**照记最后一次实测的 `FAIL`**，
  并注明修复未复验——两句都要在，少任何一句都是失真。

**六项 `PASS` 里没有一项来自模型自述。** 四项来自零模型调用的确定性判据，
两项（AC-04/05）来自当前图上的实跑证据 + 对 Dify 节点执行记录的复算。

## 二、技术债条目

### TD-UAPP-01｜完整主故事的第一轮交付不稳定　**未偿还**

**事实**：同一条冻结输入 `UAPP-FULL-01 / T1`，一次产出了完整内容制作依据并把产物与版本
写进 M2（`043f8079…`，库中可查）；另一次接缝判定输入不足，返回精确缺口「这条内容对观众的
承诺是什么」，未交付、无产物。两次输入逐字节相同。

**归因**：能力侧的输入充分性判断 + 模型波动，**不是画布的接线缺陷**。
画布在两种情况下的行为都正确（交付则登记，不交付则不登记）。

**后果**：T1 不交付时，T2 没有可发布的版本、T3 没有可挂载的对象，
`UAPP-FULL-01` 整条链无法在一次会话内演示完，故判 `FAIL`。

**处置须由 Founder 裁定**，执行侧不自行选择：① 冻结判据里的 T1 输入本就不够充分
（缺显式的「内容承诺」一项），属判据设计问题，需另出判据版本重跑；② 接缝的充分性阈值偏严。
**不得靠反复采样刷成通过。**

### TD-UAPP-03｜缺口轮由对话节点接管，一次问了三件事　**未偿还，待 Founder 裁定**

**事实**：`UAPP-GAP-01 / G1`「这周想发点东西，你看着办吧」→ 系统一次问了平台、
图文还是视频、主题方向三件事。冻结判据写的是「只问真正阻塞的那一项」。

**归因**：查 M1 给对话节点的 `dialogue_directive` 原文，它只说「如实说明当前状态」，

### TD-UAPP-09｜裁定器缺少图绑定新鲜度检查　**已修复，正负控制通过**

**事实**：裁定器只比对**判据哈希**，从不比对证据里记的 `graph_sha256_at_run` 与当前已发布图。
判据不变而图改动时（本任务改过四次），它会把绑在旧图上的证据报成 `freshness: CURRENT`。
TD-UAPP-07 那六个 `STALE` 是我**人工**认定的，机器当时并不会拦。

**这是检查器缺陷，不是被测对象缺陷**：真实结论没有被它改错过（人工先一步认定了 STALE），
但防线本身是空的——下一次没人手工盯着就会漏过去。

**修复**：新增图绑定检查，不一致即整份置 `NOT_VERIFIED / STALE` 并写明跑在哪张图上。

**控制**：负向控制——八份旧证据在修复后全部由「可读成 CURRENT」变为 `STALE`，
并各自指出所绑旧图（`f36e788d…` / `e509b550…` / 空）；正向控制——当前图上的六份新证据读成
`CURRENT` 且判 `PASS`。检查器能区分正例负例。

### TD-UAPP-10｜同一张图两个哈希口径，文档间会被读成漂移　**已修复**

**事实**：Manifest 与本表记的是构建脚本口径 `c95ffbe4…`，运行器与裁定器记的是数据库原文口径
