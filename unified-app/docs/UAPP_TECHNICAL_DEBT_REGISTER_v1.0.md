## 二、技术债条目

### TD-UAPP-01｜完整主故事的第一轮交付不稳定

**事实**：同一条冻结输入 `UAPP-FULL-01 / T1`，一次产出了完整内容制作依据并把产物与版本
写进 M2（`043f8079…`，库中可查）；另一次接缝判定输入不足，返回精确缺口「这条内容对观众的
承诺是什么」，未交付、无产物。两次输入逐字节相同。

**归因**：能力侧的输入充分性判断 + 模型波动，**不是画布的接线缺陷**。
画布在两种情况下的行为都正确（交付则登记，不交付则不登记）。

**后果**：T1 不交付时，T2 没有可发布的版本、T3 没有可挂载的对象，
`UAPP-FULL-01` 整条链无法在一次会话内演示完，故判 `FAIL`。

**未偿还**。可能的处置有二，均需 Founder 裁定，执行侧不自行选择：
① 冻结判据里的 T1 输入本就不够充分（缺显式的「内容承诺」一项），属判据设计问题，
需另出判据版本重跑；② 接缝的充分性阈值偏严。**不得靠反复采样刷成通过。**

### TD-UAPP-03｜缺口轮由对话节点接管，一次问了三件事

**事实**：`UAPP-GAP-01 / G1`「这周想发点东西，你看着办吧」→ 系统一次问了平台、
图文还是视频、主题方向三件事。冻结判据写的是「只问真正阻塞的那一项」。
第二句补齐全部业务信息后仍未往下做，反过来要平台和形式。

**归因**：查 M1 给对话节点的 `dialogue_directive` 原文，它只说「如实说明当前状态」，
**没有要求问那三件事**——多出来的问题是对话节点自行添加的。且平台并非前置条件：
`FULL-01 / T1` 在没有平台的情况下照样产出了制作依据，并把平台明确列为交给 Founder 拍板的事。

**权威域**：该行为来自**逐字复用的 M1 对话节点**。改它即改 M1 已接受的对话语义，
属产品语义、归 Founder 裁定。**执行侧不自行处置，也不回头放宽已冻结判据。**

**并列如实披露**：`GAP-01 / G2` 的冻结输入本身没有点名任何能力，
而系统纪律是「不替用户选能力」，因此「补齐后应当继续产出」这一预期**可能是判据当初写得不准**。
但判据已冻结，看到结果之后不得修改，本轮仍按写下的判据判 `FAIL`，此项单独登记、不追溯。
