## 一、裁定原文要点（逐条，不改写）

1. 当前交付只证明六项能力**物理可达**，没有证明**自然语言意图能够自动路由**。
2. 「有个账号一直没流量，怎么办」以及后续「用对应的专业能力来分析」**均属合法自然语言入口**。
   系统必须内部识别适用路径并**实际调用**专业能力，
   **不得要求用户点名模块、选择 capability 或再次确认是否调用。**
3. 用户意图明确时**直接执行**；确有决定性业务缺口时**只问一个**最高影响问题。
4. **不得在没有实际启动能力调用时声称**「已经转交」「正在推进」「等结果出来」。
5. 本轮**只**修统一 Canvas 的意图—能力路由桥接层。
   未证明必要前**不得**修改 M1 编译器、M2、最终 M3、Seam 或六能力应用。
   **不得**新增第二应用、第二运行时或固定全链。
6. 修复后建立**新 Candidate Manifest**，冻结三条定向用例。
7. `PASS` **必须以实际 Dify 节点调用为准**：专业能力真实执行、返回真实分析或精确缺口、零内部字段泄漏。
   **普通对话节点声称「将调用」不构成 PASS。**
8. `UAPP-AC-02` / `AC-05` / `AC-06` / `AC-12` **保持 `FAIL`/`RETURN`**，直到上述路径复验成立。
9. **`main` 合并继续禁止。**

## 二、这条裁定改变了什么（权威事件，不是执行侧的判断）

### 2.1 状态下调（A2 允许：有权者决定）

| 验收项 | 裁定前 | 裁定后 |
|---|---|---|
| UAPP-AC-02 | `PASS / CURRENT` | **`FAIL`** |
| UAPP-AC-05 | `PASS / CURRENT` | **`FAIL`** |
| UAPP-AC-06 | `FAIL` | `FAIL`（维持） |
| UAPP-AC-12 | `NOT_VERIFIED` | **`RETURN`** |

AC-02 / AC-05 此前的 `PASS` 由执行侧的确定性判据与六例实跑支撑，**那些判据本身没有出错**——
它们证明的是「能力物理可达」「start 零输入变量」。Founder 指出的是**判据覆盖面不够**：
物理可达不等于自然语言能自动路由。这是产品语义域的裁决，执行侧不得辩驳，照单下调。

### 2.2 推翻了一条执行侧的既有设计决定

统一 Canvas 的路由节点此前明确写着「不做意图识别、不替用户选能力」，
理由是「替用户选能力」被视为越权。**Founder 裁定推翻了这条**：
路由责任本就在统一 Canvas，识别意图不是越权，**要求用户点名模块才是失职**。

该注释与实现已按裁定改写，改动只落在 Canvas 自己的节点上。

### 2.3 受保护面在本轮未被触碰

裁定明令「未证明必要前不得修改 M1 编译器、M2、最终 M3、Seam 或六能力应用」。
本轮**一个字都没改**上述任何一处，理由是根因归属清楚且有证据：

- M1 shadow 实测输出 `route_intent: "DISCUSS"`、`requested_capabilities_text: ""`
  ——M1 如实记录了「用户没点名任何模块」，这是它被接受时的设计；
- M1 compiler 实测输出 `needed_capabilities: []`，
  但同一份 `per_capability` 里**六项全是 `reachable_if_requested: true`**；
- Canvas 路由节点只读 `needed_capabilities`，于是落到 `DIALOGUE`。

**最高失效节点是 Canvas 的桥接层**，不是 M1。M1 提供的信息足够，是没人把它桥到能力上。
证据：`evidence/UAPP_RUN_diag_intent01.json`。
