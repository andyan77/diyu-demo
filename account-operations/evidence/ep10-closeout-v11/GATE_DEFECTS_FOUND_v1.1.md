# 载体 v1.1 闸门的实测缺陷清单

> 这些缺陷**由本轮修复引入**，不是第 3 轮遗留。登记在此是为了让它们进入下一轮的修复面，
> 而不是等收口时才说。发现来源逐条标明，全部可复核。
> 本文件在四名判定者全部交付后一次写定，涵盖 82 次运行的全部实测。

---

## 总结论先说

**原来的两个缺陷修好了。修复本身引入了五个新缺陷，其中一个是设计根基错误。**

| | 原缺陷 | 本轮实测 |
|---|---|---|
| 一 | `missing[]` 自述不可靠（附件已加载却说未加载） | **58 次运行零复发**（保真 9 + 行为 49，`manifest_contradiction` 全为 0） |
| 二 | 必填项未被结构性强制 | 行为 49 例：`不足` 从 5 降到 2、`失败` 从 1 降到 0；第 3 轮失败的 `AC-06`、不足的 `AC-02`/`AC-08`/`AC-09` 本轮全部成立 |

代价是下面五条。

## 缺陷 A · 闸门给零交付盖了合规章

**发现者**：保真 ECC 独立判定者；执行侧复核属实。
**证据**：`evidence/ep06-runtime-fidelity-dify-v11/G6-attachment-unloaded.json`

```text
draft_raw = "<think>\n<!--dify-deepseek-reasoning-->`\n</think>"     ← 模型零正文
operating_judgment = "[参考文件加载状态] 不适用：参考文件未加载。"     ← 用户可见交付共 23 字符
post_gate_report.gaps_closed = true                                  ← 闸门报合规
```

补齐节点插了一句话，复检节点据此判定"缺口已闭合"。**一份零判断的交付通过了闸门。**

**为什么比原缺陷更坏**：v1.0 的失效是"漏写了但读起来顺"；v1.1 的失效是"什么都没有，而系统盖章说合规"。防护装置制造虚假信心，比没有防护更危险。

**复现率**：保真 9 例中 1 例；行为 49 例中 0 例。
**修法**：闸门增加最低实质产出门——剥掉标签与空白后的正文低于阈值 ⇒ `empty_or_trivial_delivery`，`needs_fix=yes`；`gaps_closed` 必须同时要求正文非空。

## 缺陷 B · 整个闸门建在"模型如实自报"之上——这正是原缺陷否定的前提

**这是本轮最重的一条，是设计根基错误，不是边缘 bug。**

### B-1 自报行缺失 ⇒ 静默跳过全部检查（执行侧自查）

`gate_code.py` 写成 `if trig.get(k) is True: ...` / `if trig.get(k) is False: ...`。
自报行缺失时四个触发全为 `None`，**两个分支都不进**——除无条件标签外，全部标签检查被静默跳过。

**复现率**：行为 49 例中 **3 例**（`B02-1-no-matrix`、`B14-2-legit-no-content-task`、`B15-DIR-03-finished-to-pp`）；保真 9 例中 1 例。

这 3 例**碰巧**没有漏写（模型自发写全了标签，执行侧已逐例机械核对）。**不得因此认为缺陷轻微**——闸门在这 3 例上确实没有运行，"碰巧没事"不是"被保证没事"（A2：不因运气好把等级往上推）。

### B-2 自报错误 ⇒ 静默跳过（纵向 ECC 独立判定者发现，决定性）

**证据**：`evidence/ep07-longitudinal-v11-run2/E07.json`

本轮 `account_context` 的 `feedback:` 完整载有 L5（真实发布观测）、L6（人工经营结果·口头转述）、L7（窗口未结束）三条**互相冲突**的反馈。模型输出第一句：

> 「核心输入缺了——新反馈的本体还没有进来」

随即宣布零产出。四个命中的 `[冲突反馈·*]` 必填标签**全缺**——按 `SKILL.md` 自身定性，这叫「本次交付无效」。

**而闸门全绿**：模型自报「冲突反馈=否」，`gate_report` 即返回 `missing_labels: []`、`first_pass_needs_fix: false`。

判定者的原话，执行侧完全接受：

> `gate_report` 的 missing/decorative 判定由**模型自报**的 `triggers_self_reported` 驱动。……`trigger_crosscheck_advisory` 抓到了矛盾但只是 advisory。**v1.1 用「只许回抄清单」修好了参考文件那一项，其余四个触发项仍跑在自报上。**

### 执行侧的责任认定

修缺陷一时得出的原则是：**「凡是能从输入里逐字抄的事实，就不要让模型回忆」**——这句话逐字写在 `SKILL.md` v1.1 里。

然后修缺陷二时，把整个闸门建在**模型自报四个触发标志**上。一个会漏写探索六项的模型，同样会自报「探索提案=否」。**用一条原则修好了第一个缺陷，又在第二个缺陷上违反了同一条原则。**

执行侧的 `trigger_crosscheck` 实际抓到了 E07 的矛盾，但被设成 advisory 而非阻断。**设成阻断，E07 就被拦住了。**

**修法**：触发判定不得单独依赖自报。至少三选一——(a) `crosscheck` 升为阻断（自报与正文措辞矛盾即 `needs_fix`）；(b) 触发改由**输入**侧机械判定（冲突反馈可由 `feedback[]` 的证据身份组合直接算出）；(c) 自报缺失或与 crosscheck 冲突时 fail-closed。执行侧倾向 (b)+(c)：能从输入算的就别问模型。

## 缺陷 C · 闸门标签是候选臂的唯一指纹，A/B 盲评因此失效

**发现者**：三名互不通气的盲评者，在各自的协议自检节里给出同一结论。

> 判定者 1：「`[参考文件加载状态]` 出现在 01=甲、02=乙、03=丙；散文体出现在 01=乙、02=丙、03=丁，**可用纯结构指纹机械还原**」
> 判定者 2：「`[参考文件加载状态]`＋方括号字段名这条特征在三个场景分别落在甲、乙、丙」
> 判定者 3：「四条臂的标签在三场之间做了 +1 位移」

揭盲核对：候选臂 `B` 正是 `甲01 / 乙02 / 丙03`，与三人的描述**逐场景吻合**。

**两层问题**：

1. **标签指纹**：四条臂里只有候选带 `[参考文件加载状态]`。看三个场景即可定位，**不需要读任何 sealed mapping**。
2. **置换退化成轮换**：实测三场排列为
   `01: B, Bprime, Aplus, A` → `02: Aplus, B, Bprime, A` → `03: A, Aplus, B, Bprime`，
   近乎完美的 +1 位移。三个场景 + sha256 派生排列不足以保证跨场景不可追踪。

**执行侧的责任**：`_arms_and_holdouts_v2.json` 的 `known_confounds` 写了这一条，但写成了「不保证风格**不可猜**」——实测是「**可机械还原**」。把确定性漏洞写成了概率性风险，低估了。

**`ADDENDUM_001` 的事后核验防错了东西**：它核验判定者有没有读 mapping 文件，而去盲根本不需要读文件。

**处置**：`M3-AC-18` 与 `M3-AC-01③` 本轮 `NOT_VERIFIED`（按冻结件 §7，不是 `FAIL`）。

**硬门结果另存为独立观察**，不作为任一 AC 的通过或不通过依据：

| 臂 | 三名判定者合计判定的硬门实质退化 |
|---|---|
| `B`（候选） | **0** |
| `Aplus`（基线＋附件） | 0 |
| `A`（胜任基线） | 4 |
| `Bprime`（删掉 M3 的消融臂） | **8** |

**不能用来救 AC-18 的理由**：三名判定者的自检节都显示他们把消融臂 `Bprime` 误认为基线、**未识别出候选 `B`**。这提高了硬门观察的可信度，但盲评的**前提**已被证伪——不得因为"通道实际没被利用"就把等级往上推。

**修法未定，且不在执行侧权限内**：标签指纹是候选的真实形态，无法靠盲评协议消除。可选路径（去盲化预处理 / 逐场景单发 / 换取证方法 / 接受 `NOT_VERIFIED`）各有代价，**属判据方法变更，需 Founder 决定**。

## 缺陷 D · 闸门标签违反 Skill 自己的输出条款

**发现者**：盲评者 2，在**完全不知道任何背景**的情况下，按冻结 Rubric §5.3「共同质量底线」维度判：

> 共同质量底线四份都有该扣的：**机器状态泄漏（`[参考文件加载状态]`）**、模板占位（"- 无。"、逐卡重复的边界句）

对照 `SKILL.md` 自己的〈输出〉：

> 结构化业务语义与证据引用供系统内部和下游消费，**默认不向用户暴露状态机、哈希、内部字段或长篇自检**。

以及 v1.1 执行侧在〈必填项闸门〉里写的：

> **标签是锚点，不是表单**：……不另起自检段、不回显触发判断过程、**不暴露内部字段**。

`[参考文件加载状态]` 本身就是一个内部字段名，直接出现在用户可见交付里。**规则是执行侧写的，违反的也是执行侧。**

**修法**：无条件标签这一项改为不进入用户可见正文（走结构化侧信道），或改写成不含字段名的自然语言。其余触发类标签是实质业务内容，可保留，但同样需复核措辞是否读起来像内部字段。

## 缺陷 E · 裸标签形态整体逃逸检测

**发现者**：行为 ECC 独立判定者。
**证据**：`evidence/ep06b-runtime-behavior-v11-run2/B08-P-single-anomaly.json`

该例模型在原稿末尾自发回显了一段自检，写成**裸标签**形态：

```text
[参考文件加载状态] 已列明。          ← 纯空洞
[冲突反馈] 已按规则处理（…）          ← 同义反复
[暂定锚点] 不适用                     ← 触发未命中的装饰性填空
[无内容任务] 不适用                   ← 触发未命中的装饰性填空
```

另有残缺空标签 `[]` 与半截字段名「账缺失」。

**该例 `gate_report.decorative_labels` 为 `[]`** —— 闸门按带 `·` 后缀的完整子标签精确匹配，**裸标签形态整体逃逸**，4 处装饰性填空一处未检出。

判定者已核对：这段出自 `draft_raw` 原稿尾部，与最终输出逐字一致，**不是补齐节点写的**。

**修法**：标签匹配改为「前缀族」匹配（`[探索·` / `[暂定锚点·` / `[冲突反馈·` / `[无任务·` 以及它们的裸形态 `[探索]` / `[冲突反馈]` …），并把残缺标签 `[]` 单列为一类失效。

## 缺陷 F（产品级，与闸门无关）· 链式投影因一次零产出永久丢内容，无任何机制察觉

**发现者**：纵向 ECC 独立判定者。

E07 那份 523 字符的零产出回填进投影后：

> 把 P1/P2/P3 与四周节奏从投影中挤掉，E08 起再未出现，**无任何机制察觉**。

这在持续运营场景里比漏写严重得多——它是**静默的状态损坏**，用户看不到，下游也看不到。

**这不是闸门缺陷，是产品的链式投影缺陷**，修法涉及持久化与投影语义，不在本轮修复面内，登记为新任务候选。

## 执行侧自己的两处流程错误（不推给判定者）

### 错误 1 · `_steps.json` 未及时复制，导致纵向判定未用逐步 Oracle

纵向判定者的 allow-list 只含 `ep07-longitudinal-v11-run2/`，而逐步 Oracle 文件 `_steps.json` 当时仍在被禁读的目录里——执行侧是在启动**行为**判定者前才复制的，晚了一步。

判定者的处置是正确的，且自己声明了边界：

> 我用 §4/§6.5/§7 + SKILL 机械判据重建了判准。凡 Oracle 更严处我的 `成功` 可能偏松；`不足`/`失败` 在更宽判准下已命中，不会翻转。

**后果**：纵向的 `失败`（E07）与 `不足`（E04）结论**稳**；10 个 `成功` 必须降级为「在重建判准下成立，未经冻结逐步 Oracle 核对」。这是执行侧造成的取证损失。

### 错误 2 · 隔离边界画错，判定者无法确认载体授权链

保真判定者与纵向判定者**各自独立**撞上同一个副作用：冻结件 §1/§5 锁定的是直连 DeepSeek + `af61b82` 版 Skill，本轮实际是 Dify 图 + `carrier_revision v1.1`，而授权链在被禁读的 `M3_ECC_REBIND_002_FROZEN_v1.0.md` 里。

两人都**没有推断**，直接标 `NOT_VERIFIED`——**做法完全正确**。

**责任在执行侧**：授权链本该以摘录形式随判定任务下发，而不是整份禁读。两名判定者独立撞上，说明这不是偶然，是边界设计错误。

**后果**：本轮全部 ECC 的「所判对象即冻结件所锁定对象」这一条，**由判定者侧未核验**，只有执行侧的单方声明。需在下一轮以摘录形式补上，或由独立收口审查者单独核验。
