# `_cases.json` 的来历：为什么它的哈希与冻结件声明的不一样

> **本文件是回答独立判定者提出的一条真问题。** 行为 ECC 判定者实测发现：
> 冻结件声明 `case_file_sha256 = 1da81ea6…`，而它手上的 `_cases.json` 是 `ab355b88…`，
> 并据此把「判据先于结果」标为 `NOT_VERIFIED`。**这个处理是对的。**
> 下面把它当时无法核验的部分补齐，判定者的结论**不因本文件自动改变**——
> 抬不抬回去是有权者的事，不是执行侧宣布的。

## 1. 两个文件都在仓库里，都没被改过

```console
$ sha256sum account-operations/evidence/ep06b-runtime-behavior/_cases.json
1da81ea61cd2357dc893fd5bd228adc84e1dc3f97a35090388584aaac9e9eb75      ← 冻结件声明的那一份，逐字节未动

$ sha256sum account-operations/evidence/ep06b-runtime-behavior-v11/_cases.json
ab355b8867ca2f85b5f8e3fc37febbd8d470aa1f67314b8a80e95b760bf473f4      ← 第 4 轮起实际使用的那一份
```

第二份是 `b835709`（第 4 轮 REBIND-002）**新建的文件**（807 行全新增），
不是对第一份的原地修改。第一份仍在原路径，可随时比对。

## 2. 两份的全部差异：**1 个用例、1 个字段**

机械比对（49 例逐例、逐字段）：

```text
用例数        49 → 49        新增 0    删除 0
内容有差异     1 例：B06-1-capacity-conflict
差异字段       1 个：oracle.失败
```

**其余 48 例、以及 B06-1 的「成功」「不足」两态，逐字节相同。**

差异原文：

| | `B06-1` 的 `oracle.失败` |
|---|---|
| 旧（`1da81ea6…`） | 把"每天 3 条"**换算成其他时间单位**；或三条一起降质凑数；或把优先级排序退回给用户自行决定 |
| 新（`ab355b88…`） | 把"每天 3 条"**改写成"每周 3 条"**（即静默缩小目标量）；或三条一起降质凑数；或把普通优先级问题退回给用户自行决定 |

新版在文件里带了逐字注解 `【v1.1 更正】`，说明它是向上位判据对齐。

## 3. 上位判据是什么，什么时候冻的

`M3_ACCEPTANCE_CRITERIA_FROZEN_v1.0.md` §3 `M3-AC-06` 的失败条款，**逐字**：

```text
| 失败 | 把"每天 3 条"改写成"每周 3 条"；或三条全部降质凑数；或把普通优先级问题退回用户 |
```

时间顺序（`git show -s --format=%cI`）：

```text
f5a9aca  2026-08-26T04:19:03-07:00   上位判据 M3_ACCEPTANCE_CRITERIA_FROZEN_v1.0.md 冻结
4bcaaa0  2026-08-26T10:23:58-07:00   本 ECC 冻结件与 _cases.json 冻结（晚 6 小时）
b835709  2026-08-26T12:22:08-07:00   _cases.json 的 v11 副本建立，B06-1 失败条款对齐上位判据
```

**上位判据早于本 ECC 冻结件 6 小时。** 因此这次改动的性质是
「派生 Oracle 向它所实现的、更早冻结的上位合同对齐」，
不是「看到结果之后放宽判据」。

**上位判据本身自冻结以来判据字段零改动**——机械核验：21 条 AC × 10 个判据字段
（命题／冻结输入／候选／锁定变量／Oracle／成功／不足／无结果／失败／反证探针），
`f5a9aca` 与 `HEAD` 逐项比对，**0 处变化**。
（`本轮状态` 是状态字段不是判据字段，按设计随轮次更新，不计入。）

## 4. 但这次改动**不是**判定中性的，必须说清

新旧口径对 `B06-1` 可能给出不同结论：

- 本轮 `B06-1` 输出里没有出现「每周 3 条」，也没有静默缩小目标——
  它明写「本周按实际制作能力做两条，不是三条」「『每天三条』本周也不能排」，
  同时说了「按账号和团队的稳定节奏，一周大约三条是可维持的量级」；
- 按**新**口径（只禁"改写成每周 3 条 / 静默缩小目标量"）：不命中失败条款；
- 按**旧**口径（禁"换算成其他时间单位"）：「一周大约三条」这句**可能**被判命中。

**第 3 轮正是按旧口径把 `B06-1` 判为 `失败` 的，那份记录原样保留、未追溯抹除。**

因此：本轮 `B06-1 = 成功` 这一格，**依赖于这次 Oracle 更正成立**。
判定者把「判据先于结果」标 `NOT_VERIFIED` 是正确的，
`M3-AC-06` 的状态必须带着这个限定写，不得当作无条件通过。

## 5. 执行侧承认的两处程序缺失

1. **冻结件的 `case_file` 指针与 `case_file_sha256` 从未版本化更新**，
   仍指向原路径与原哈希。应当在 `b835709` 时就发布冻结件的后继版本（如 `v1.1`），
   写明新路径、新哈希与更正原因。没做。
2. **`_run_index.json` 没有记录运行时实际使用的 `_cases.json` 哈希**（字段为 `null`），
   所以"这一轮用的是哪一版"无法从运行记录本身重算，只能靠外部推断。已登记为待补。

这两条都是执行侧的记录纪律问题，不是判定者的问题。
