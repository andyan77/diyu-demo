## 1. 产品目标与当前缺口

### 1.1 目标

已经有三份内容决策 Skill 跑通并留下真实运行证据：

```text
Matrix Architect → Campaign Orchestrator → Content Brief Architect
```

它们回答「做不做、做什么、为什么、由谁做、接不接得住」，
终点是一份人可以接受的 Content Brief。

内容生产链 V1 要回答后面三个问题：**怎么说出来、怎么拍出来、怎么发出去**，
终点是**可拍、可剪、可发布的内容生产包**。

### 1.2 当前缺口

| 缺口 | 现状 |
|---|---|
| Brief 之后没有承接者 | Brief 明确拒绝输出口播、分镜、标题、封面与发布文案，而没有任何一份 Skill 负责它们 |
| 制作条件从未被建模 | 几个人、多少时间、有没有设备场地，从未作为正式输入进入任何一环 |
| 平台与行业知识没有承载体 | 平台规则、可观察做法、趋势判断散落在讨论里，没有分级，也没有读取边界 |

V1 要补的就是这三处，**不多补**。

## 2. 首要目标与轻量化裁决

```text
Decision ID：PRD-DECISION-LIGHTWEIGHT-DELIVERY-FIRST-V1
状态：ACTIVE
裁决人：Founder
裁决日期：2026-08-21
```

**本项目的主战场是 Dify，不是文档仓库。**
衡量成败的第一标准是**产品功能画布是否成功交付并跑通**，
不是文档是否完备、治理是否严密、状态是否穷举。

由此形成三条硬约束，适用于 `P0`—`P9` 全部阶段：

1. **轻文档化**：文档只写「不写清楚就会做错」的部分。
   能在 Dify 画布里直接验证的，不在文档里预先规定。
2. **轻治理化**：禁止过重的治理文档化——不新建注册表、判据库、错误码表、
   状态迁移图、编号算法、变更日志、Gap Register 或索引文件；
   不为对称、完整或美观增设层级。
3. **冲突时以交付优先**：本文件、合同与研究协议中任何一条，
   若在实际执行中变成阻碍画布交付的形式负担，
   由 Founder 裁决删除或简化，不得反过来要求交付迁就文档。

本裁决优先于本轮之前的一切执行 Prompt 与文档表述。
与之冲突的旧表述以本裁决为准。

## 3. 三份生产 Skill 的宏观链路

```text
Content Brief（已接受）
→ Creative Script Architect     把 Brief 变成完整内容表达与脚本
→ Production Director           把已接受脚本与真实制作条件变成可拍、可剪的生产包
→ Publishing & Packaging        把已接受生产包、真实成片状态与平台状态变成可发布包装
```

宏观边界只有三条，**P0 只冻结到这里**：

1. **说什么归第一段**：内容本身要表达什么，由 Creative Script 决定。
2. **怎么拍怎么剪归第二段**：镜头、现场、声音、剪辑与降级方案，由 Production Director 决定。
3. **对外怎么呈现归第三段**：标题、封面、发布文案、标签与平台规格，由 Publishing & Packaging 决定。

三段的**详细方法、字段与相互接缝，本轮不裁决**，
由 `P1`—`P4` 研究与 Founder 集中裁决决定。
需要延后的接缝问题清单见
[合同第 9 节](CONTENT_PRODUCTION_CHAIN_CONTRACT_v0.1.md)。

## 4. Production Profile 与可行性判断的定位

Production Profile 与 Production Feasibility Gate 是三份生产 Skill 的**共享前置条件**，
**不是第四份 Skill**，不产生内容判断。

它用大白话记录和判断五件事：

| 模式字段 | 大白话 |
|---|---|
| `requested_mode` | 用户希望怎么做 |
| `available_mode` | 现在真实能调动的人、设备、时间、场地和素材 |
| `minimum_viable_mode` | 最低能跑起来的做法 |
| `recommended_mode` | 系统建议的做法 |
| `accepted_mode` | 用户最终接受的做法 |

可行性判断的结果只有四种：**可执行 / 降级后可执行 / 需要补一项资源 / 当前不可执行**。

两条纪律：

- **不得要求用户自行完成内部枚举映射。**
  用户用自己的话说明制作条件即可，把话折算成档位是系统的事。
- **「用户尚未声明资源」不等于「已经确认缺少资源」。**
  未声明时按「需要补一项资源」处理并向人询问，不得默认判为不可执行，
  也不得从夹具推断一个档位填上去。

「制作方式具体分成哪几档」属于待研究项，`P0` 不冻结（见合同第 9 节）。

## 5. P0 冻结决定

`P0` 只冻结以下九条。除此之外的一切，`P1`—`P4` 可以自由研究与提议。

1. 内容生产链由三份核心 Skill 构成，宏观职责如第 3 节；
2. Production Profile 不是第四份 Skill，只是共享前置条件（第 4 节）；
3. 已被人工接受的 Content Brief，**全部字段的业务语义都是上游决定**，
   生产 Skill 可以展开与实现，不得重新选择、扩大、缩减或替换；
4. `P1`—`P3` 由 Founder 手动在 Claude Code 与 Codex 两个独立窗口执行，
   首轮提交前互不可见；研究阶段不进入 Dify、不启动后台代理群；
5. `P4` 由集中评审加 Founder 裁决，模型只能给推荐、代价与路由；
6. `P5`—`P7` 顺序施工，后一份 Skill 必须使用前一份已接受的真实输出；
7. 发布反馈学习延期（第 9.1 节）；
8. 模型策略与平台未确认边界（第 6.3、6.4 节）；
9. 轻文档化与轻治理化裁决（第 2 节）。

- 不得通过暗号、藏码、诱导跳转等方式规避平台规则；
- 不得因用户愿意承担风险而生成明确违规手法。

```text

 ↓
```

### 7.1 各阶段门禁

| 阶段 | 谁执行 | 门禁 |
|---|---|---|
| `P1`—`P3` | Founder 手动开启 Claude Code 与 Codex 对应窗口 | 两窗口读取同一个 `P0` Commit；同一组核心研究问题；不同优化视角；提交前不得读取对方结果；不启动后台代理群；不运行 Dify；不建设 Skill 或 DSL |
| `P4` | 集中评审 ＋ Founder 裁决 | 读取六份已冻结研究结果；对冲突、重叠、空档与条件差异集中评审；模型只提推荐、代价与路由；不按模型数量、品牌或多数票裁决 |
| `P5`—`P7` | 顺序施工 | 后一份必须使用前一份已接受的真实输出；不得在施工阶段重开无边界研究；不得静默修正前一份 Skill |

| `P9` | 独立只读审计 | 只审运行真实性、边界继承、交接与证据；不修改；不选择性重跑；不代替 Founder 判断内容优劣；只输出 `GO` / `NO-GO` 与缺陷账本 |

首轮按风险覆盖约 **8—12 个高价值场景**。
**不预设必须达到 40 条测试**，是否扩样由真实失败触发。

三者可在以下条件全部成立后并行启动：

1. 本文件、合同与研究协议三份已落盘并提交；

各窗口**只研究自己那一份 Skill 的职责范围**，不得跨界，不得提前编写任何 `SKILL.md`。

## 8. V1 完成定义

内容生产链 V1 在**同时满足**以下四条时成立：

1. 三份生产 Skill 在 Dify 上落盘为可运行画布，并留下真实运行证据；
2. 至少一条已接受的 Content Brief 内容单元，跑完脚本 → 生产包 → 发布包装全链；
3. 产物之间可追溯：每份产物能说清它依据的是哪一份上游产物和哪一次接受记录；
4. 有 Skill 与无 Skill 的同条件对照已完成，且由 Founder 盲审给出判断。

### 8.1 明确不要求

- 真实拍摄成片；
- 自动剪辑或导出视频；
- 自动发布平台内容；
- 内容已获得良好数据；
- 系统已从发布结果中学习。

### 8.2 不得制造通过

不得通过修改既有文件消除冲突、修改验收标准、删除失败或冲突证据、
把假设写成事实，或以文档数量替代真实运行证据。

## 9. 延期事项与已知限制

### 9.1 发布反馈学习延期

```text
Decision ID：PRD-DECISION-FEEDBACK-LEARNING-DEFERRED-V1
状态：DEFERRED
```

V1 不建设：发布表现抓取、账号自动搜索与学习、自动经验回写、
长期反馈学习、Skill 自动更新。

这些属于后续反馈学习层，**不进入 `P0`—`P9`**，不计入完成标准，不作为验收项。

执行代理在 `P1`—`P3` 中仍可以使用合法网络搜索开展研究；
这不等于把搜索工具接入产品，也不构成对本裁决的突破。

### 9.2 单账号内容策划能力：已登记，未启动

```text
Decision ID：PRD-DECISION-SINGLE-ACCOUNT-PLANNER-REGISTERED-V1
状态：REGISTERED_NOT_STARTED
登记日期：2026-08-21
启动条件：由 Founder 在需要时显式启动，执行侧不得自行开工
```

按 Founder 裁决与本文件第 2 节轻文档化原则，本缺口**并入本节登记，不另立文件**。

**缺口**：当前系统有矩阵设计能力与 Campaign 协同能力，
但没有**单账号持续经营与内容机会发现能力**。
「今天某账号该发什么」「这段素材该由谁做成什么」在系统内没有承接者。
而现实中企业的多数日常内容，并不是每次启动一场多账号 Campaign。

**这是硬编码约束，不是概念空白**（据 `main@727c744` 核验；
相关文件不在本分支，故只写文件名）：
`V1_DEMO_INTEGRATION_CONTRACT_v0.1.md` 第 5.5 节写明
「Content Brief 只能消费 `USER_ACCEPTED` 的 Campaign」，第 1 节写明三份 Skill
固定分支、映射写死；`DIYU_DEMO_V1_MAIN_CHATFLOW_v0.1.yml` 只有
`matrix` / `campaign` / `content_brief` 三条路由，`requested_skill` 枚举无单账号取值。

**它不是 Campaign 的 N=1**——差别不在账号数量，而在什么是给定的、什么是要搜索的：

| | 给定 | 要搜索的 |
|---|---|---|
| Campaign | 经营任务 | 哪些账号、什么顺序、怎么接力 |
| 单账号策划 | 账号 | 最近发生了什么值得讲、够不够独立成篇 |

Campaign 跑 N=1 会让参战组合、接力关系、主承接人、数量上限、顺序全部失效，
**而「该讲什么」仍未被回答**——Campaign 从来是继承任务，不搜索选题。
因此建议它作为**第四份决策 Skill，与 Campaign 平行**，不放在 Campaign 之下。

**真正的瓶颈是记忆，不是策划**：现有三份 Skill 没有任何一环记得某个账号说过什么。
只加 Skill 不加这份记忆，只能从责任卡与夹具重新推导，
会稳定生成看起来合理但互相重复的选题。

与第 9.1 节的关系，这里必须分清：

| | 是什么 | 是否被 9.1 延期 |
|---|---|---|
| 已发布内容清单 | 我们自己产出过哪些内容、归给哪个账号、讲过什么判断 | **否**，只是归档自有产物，与既有 RUN MANIFEST 同类 |
| 发布表现数据 | 播放、评论、涨粉、成交回流 | **是**，V1 不建 |

重复度判断只需要前者。去掉「最近顾客评论与问题」一项后，本能力在当前边界内可以成立。

**今天缺的输入**：最近真实经手的事件、最近上传的图片视频录音、
已发布内容与重复度、正在持续的内容系列（以上可建）；
最近顾客评论与问题（已由 9.1 延期）。
其余输入——账号长期使命、权威来源、表达边界、关系姿态、可公开事实、
出镜与产能、平台与生产条件——今天已经具备。

账号责任卡的挂载已有先例：`V1_DEMO_INTEGRATION_CONTRACT_v0.1.md` 第 6 节说明，
责任卡不在下游夹具包里，该位置由**已被接受的 Matrix 产物**占据。
这与「Matrix 是低频初始化能力」一致——不必每条内容重跑，但其已接受产物是必需输入。

**它应输出单账号内容决策，不是脚本**：

